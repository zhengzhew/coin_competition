# 第三子赛项：棋盘模拟与 3D 模拟实现计划

编写日期：2026-09-24
项目：`coin_competition`
状态：M1 与 M2 基础试用功能已实现，正式 DEMO 待补充（实施记录见第 13 节）
参考平台：[https://hd.testing.hetao101.com/](https://hd.testing.hetao101.com/)

## 1. 目标与已确认要求

在现有项目中新增第三个子赛项，支持收集、摆放两类任务。每类任务同时提供自动、手动两种操作方式，每种操作方式又支持棋盘模拟和 3D 模拟，共形成 8 个玩法组合。

**3D 模拟参考上述平台的体验，在我们自己的项目和部署环境中重新实现。** 场景、控制、仿真逻辑及资源由本项目提供；外部平台作为研究参考，不作为运行时依赖，也不通过 iframe、网页跳转或远程接口代替本地实现。

已确认的定义：

- **棋盘模拟**：沿用现有走格子形式。即使画面使用立体模型，只要规则仍按格子运行，就归入棋盘模拟。
- **3D 模拟**：在本项目中重建参考平台所代表的三维仿真体验。运动、碰撞和物体交互的具体实现，根据参考研究与玩法 DEMO 确定。
- **自动**：学生编写程序，由程序驱动机器人执行动作；不预设自动寻路或 AI 代做。
- **手动**：学生通过键盘按键直接控制机器人。
- 用户正在编写各玩法 DEMO，先完成基础框架，再逐项落实具体玩法。
- 第三个子赛项的正式名称尚未确定，界面暂称“第三子赛项”。

│   ├── 自动（程序控制）
│   │   ├── 棋盘模拟 → DEMO 列表 → 玩法页
│   │   └── 3D 模拟 → DEMO 列表 → 玩法页
│   └── 手动（键盘控制）

│       └── 3D 模拟 → DEMO 列表 → 玩法页

### 3.2 玩法页

- 顶部显示当前位置，例如“第三子赛项 / 收集 / 自动 / 3D 模拟”。
- 显示 DEMO 名称、任务目标和必要规则。
- 主区域显示棋盘或三维场景。
- 自动模式提供程序编辑、运行、停止、重置和执行状态。
- 手动模式提供按键说明、开始、停止、重置和控制反馈。
- 任务有完成判定时显示进度和结果；尚未制定评分时只显示任务完成情况。
- 提供返回 DEMO 列表、返回分类的入口，返回时恢复之前的选择。
- 未接入内容显示“DEMO 准备中”；基础验证样例明确标注“功能验证样例”。

## 4. 交付范围与里程碑

### M1：分类和导航框架

交付第三赛项独立入口、两大类、8 个玩法组合、DEMO 配置、统一玩法页外壳，以及待开放状态。

验收时可以完整浏览和定位 8 个组合。此时没有具体内容的组合允许处于待开放状态，不能将其认定为玩法已经完成。

### M2：基础功能可操作

交付棋盘运行适配、本地 3D 基础场景，以及自动和手动两类控制。建议建立 4 个最小功能验证样例：收集棋盘、摆放棋盘、收集 3D、摆放 3D，每个样例分别支持自动和手动。

这些样例用于验证“能进入、能操作、能触发基本交互、能结束、能重置”的完整流程。交互规则在参考研究后确定；用户 DEMO 若已提供，优先用其最小片段完成验证。工程样例不替代用户正在编写的正式玩法。

**基础功能阶段的完成标准是 M1 + M2。** 只有分类页面和占位内容，不能算本地 3D 模拟完成。

### M3：用户玩法 DEMO 逐项落地

按用户提供的内容补齐地图、场景、规则、指令、按键、目标与完成判定。每个 DEMO 单独验收、单独开放；无需等待所有 DEMO 完成后才试用。

正式评分、排行榜、教师统计和服务端成绩核验，在玩法及评分规则确定后另行接入。初期试用只记录本地过程和结果，不产生正式比赛成绩。

## 5. 本地 3D 模拟方案

### 5.1 先研究参考，再确定复刻边界

参考研究需要形成一份可核对的行为清单：

| 研究项 | 需要明确的问题 | 产出 |
|---|---|---|
| 场景与视角 | 默认视角、相机拖动、缩放、跟随、场地边界 | 页面和操作流程说明 |
| 机器人运动 | 连续或离散移动、转向、速度、停止方式、方向参照 | 控制行为表 |
| 程序控制 | 支持的指令、参数、顺序执行方式、停止行为 | 最小指令集合 |
| 收集 | 接触收集、主动抓取或其他机制，是否存在容量限制 | 收集状态及判定条件 |
| 摆放 | 物体如何持有、释放、落地、进入目标区域，是否需要朝向或堆叠 | 摆放状态及判定条件 |
| 物理行为 | 是否需要惯性、重力、摩擦、刚体碰撞、推挤、堆叠 | 物理范围与实现选择 |
| 资源表现 | 机器人、物体、地面和目标区域的必要视觉特征 | 本项目资源清单 |

参考页面暂时不可访问时，分类导航和 DEMO 配置仍可推进；运动与物理部分保留明确的待定项，不能把未查看的效果当作复刻完成。

### 5.2 渲染与仿真分层

- **渲染层**：优先使用项目已有 Three.js，负责模型、灯光、相机和状态显示。
- **仿真层**：负责机器人位置、朝向、动作执行、物体状态和交互判定。
- **玩法层**：负责收集或摆放的任务目标、进度、完成条件和结果。
- **输入层**：将程序指令或键盘输入交给当前模拟实例。

棋盘与 3D 可以共用任务元数据、界面约定和基础事件结构，但分别拥有运行状态及运动模型。不要将连续运动强行转换成原有“走一格”的指令，也不要把原有棋盘状态套用为 3D 物理状态。

### 5.3 基础能力

1. 场地、机器人、任务物体和目标区域可在本地加载与显示。
2. 根据研究结果建立运动模型，明确位置单位、角度单位、方向参照和动作结束条件。
3. 对连续仿真使用固定逻辑步长，渲染刷新与仿真更新分开，避免设备帧率直接改变运行速度。
4. 统一处理场地边界、必要碰撞、机器人停止和重置。
5. 按 DEMO 需要实现收集、持有、释放、摆放等对象状态及成功判定。
6. 场景切换时清理动画循环、键盘监听、观察器和图形资源。
7. 显示资源加载失败和 WebGL 不可用状态，并提供返回入口。

具体物理引擎在研究后选择：若任务只需要受控运动及简单碰撞，可先使用简化模型；若验收依赖落体、推挤或堆叠，则必须将相应物理能力纳入基础实现，不能仅靠视觉动画通过验收。物理库版本、加载方式和打包可行性在实施时验证。

全部必需的场景资源、脚本及物理运行资源随本项目交付，并在本环境提供。通过禁止访问参考域名的浏览器检查，验证玩法仍可独立运行；这不等同于承诺整个现有系统离线运行。

## 6. 自动、手动与运行状态

### 自动控制

- 优先复用现有程序编辑与受限指令校验能力；3D 指令参数在运动规则确定后补充。
- 程序先校验，再按顺序派发动作；展示当前运行状态及错误位置。
- 运行时提供停止，重置后恢复初始场景并保留当前 DEMO 的程序草稿。
- 设置与玩法相适应的运行时长、指令数量或循环展开上限，保证始终可以停止。
- 自动运行期间，机器人不接受手动移动输入；相机操作按页面设计处理。

### 手动控制

- 根据 DEMO 定义方向参照、移动、转向和交互按键，并在界面中清楚显示。
- 棋盘按离散动作处理；连续运动按按下、松开状态处理，避免依赖键盘重复频率。
- 输入框、程序编辑区获得焦点时，不将打字识别为机器人控制。
- 页面失焦、切换标签页、切换玩法或离开场景时清除按键状态，并暂停或停止运行，返回后由用户恢复。

### 进入、退出与重置（按最新要求调整）

- 一次只存在一个活动玩法实例，先停止旧实例，再进入新实例。
- 同一 DEMO 的自动与手动可以共享初始场景配置，但必须从分类页分别进入；关卡内不提供手动／自动切换。
- 程序草稿按赛项、DEMO、版本及模拟形式隔离。
- 返回分类后另选类别、模式或模拟形式时开始新的运行，不迁移正在执行的机器人状态。
- 重置恢复机器人、物体、目标进度、计时和控制状态，不只是复位相机。

## 7. DEMO 配置与接收规范

### 7.1 配置模型

建议以配置驱动入口和内容装配。一个 DEMO 可以声明多个支持的操作模式，每个组合保持独立可用状态。

| 字段 | 用途 |
|---|---|
| `competition_id` | 第三赛项标识，暂定 `third` |
| `demo_id`、`content_version` | 稳定内容标识及版本 |
| `category` | `collect` 或 `place` |
| `simulation` | `grid` 或 `simulation3d` |
| `supported_modes` | `auto`、`manual` 及各自开放状态 |
| `title`、`description`、`objective` | 列表展示、说明和任务目标 |
| `status` | `planned`、`sample`、`ready` |
| `scene_config` | 场景或棋盘配置 |
| `control_config` | 指令、按键、参数单位及约束 |
| `rule_config` | 收集、摆放和完成条件 |
| `asset_manifest` | 在本环境提供的资源及版本 |

棋盘和 3D 的配置使用不同类型校验。没有指令适配的 DEMO 不开放自动入口；没有键盘适配的 DEMO 不开放手动入口。

### 7.2 每个 DEMO 最少需要的信息

1. 所属大类、模拟形式和支持的操作方式。
2. 场景布局、起点、任务物体和目标区域。
3. 学生需要完成什么，怎样算完成或失败。
4. 可用动作、按键或程序指令，以及动作的参数和单位。
5. 收集、摆放、碰撞和重置时的具体行为。
6. 如有计分：计分方式、时间或操作限制。
7. 可运行示例、源文件或必要的视觉与操作参考。

缺失信息记录为该 DEMO 的待定项，不自动套用原有金币计分、步数上限或夹爪判定。

## 8. 路由、身份与数据边界

建议使用独立路径 `/third/`，后续可随正式命名调整。路径方案为：

```text
/third/
/third/collect/
/third/collect/auto/grid/
/third/collect/auto/grid/<demo-id>/
/third/place/manual/simulation3d/<demo-id>/
```

- URL 保存类别、控制方式、模拟形式和 DEMO 标识，支持刷新和直接访问。
- 非法组合、不存在的 DEMO 和未开放内容显示明确提示及返回入口。
- 同步验证 Vite 开发访问、构建产物及 Express 生产静态回退；若部署有 Nginx，再检查相应路径转发。
- M1/M2 使用独立第三赛项页面及本地试用数据空间，不直接挂载旧 `App` 的成绩提交流程。
- 若初期需要记录运行过程，至少带上赛项、DEMO、内容版本、类别、操作方式、模拟形式及独立运行 ID，并标记为试用。
- 正式接入后端时，新增明确的赛项和任务映射，逐项调整 API 白名单、任务编号校验、关卡查询、埋点及教师筛选；不能只扩展 TypeScript 枚举就认为后端支持完成。
- 保持原有 K/P、FK/FP 任务及历史记录的语义。第三项未支持的请求应明确拒绝，不能默认归入旷野淘金。
- 棋盘现有回放核验不直接证明 3D 成绩可信。3D 正式成绩需要独立的验证方案，在规则稳定后设计和验收。

### 3D 尺寸约定更新（2026-09-26）

按本轮确认，3D 地图使用 120 × 120 cm、12 cm 网格、左下角原点；车体为 19 × 19 cm，夹爪宽 19 cm、向前伸出 6 cm，货块占地 6 × 6 cm。渲染、坐标提示、碰撞和指令距离均按厘米统一，保持连续运动。棋盘模拟仍采用原有逐格规则。具体约定与交互容差见《第三子赛项_开发说明》。


### 接触物理更新（2026-09-26）

3D 摆放中的方块均为可推挤的动态刚体。夹取和释放对应夹爪合拢／张开，由双侧接触和摩擦形成夹持，支持空夹和滑脱，不进行吸附或固定连接。采用有限驱动力、夹紧力及地面摩擦；目标改为完整进入区域并停稳，已到位货块在任务结束前仍可被推出。当前覆盖桌面平面运动，质量与摩擦参数需实物标定，垂直抬升、翻倒及堆叠留待相关 DEMO 明确后扩展。参数、边界及校准方法见《第三子赛项_开发说明》。
