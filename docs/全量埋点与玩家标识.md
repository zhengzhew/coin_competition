# 全量交互数据与玩家 UUID 规格 V2.0

目标：能按一个玩家、一种模式、一关、一轮，还原“看到了什么、做了什么、何时做、系统如何响应、保存是否完整”。**只记录移动、最终代码或成绩不满足本次要求。**

## 1. 开始时创建与展示玩家

首次加载即调用 `POST /api/players/bootstrap`。服务器使用安全随机 UUIDv4 创建 player_uuid，生成便于教师口头核对的 display_name，如“淘金者 Q7M2”。昵称不是唯一键；完整 UUID 才是唯一身份。入口醒目显示二者，并提供复制玩家码按钮，不让学生手填身份 UUID。

如果有效玩家会话已经存在，接口直接返回原 player_uuid，并发出 identity.resumed。UUID存在服务器players表；本机保存可展示的玩家快照和恢复状态；鉴权凭据放 HttpOnly/Secure/SameSite Cookie，不放公开URL或日志。仅有UUID不能恢复身份、读数据或代提交。

### 1.1 生命周期与边界

| 情况 | 处理 |
|---|---|
| 首次进入 | 创建 UUID 和称呼，展示 identity.created；开轮前必须登记成功 |
| 请求超时重发 | bootstrap 请求带稳定 idempotency_key，由事务唯一约束返回同一玩家 |
| 刷新、再次打开、跨关、切模式 | 有效会话沿用同一 player_uuid；page_instance_id 刷新后重新生成 |
| 同电脑下一位学生 | 点“换一位玩家”，先提示旧数据同步状况；确认后新建 UUID，旧记录保留并隔离 |
| 未同步就换玩家 | 默认阻止切换，要求先同步或教师保存诊断包并明确接管；不得静默清空旧缓冲 |
| 清空浏览器数据/隐身窗口 | 若安全会话丢失，不凭展示UUID猜测恢复；自动新玩家并说明状态；教师可以身份核对后签发一次性恢复码 |
| 换电脑 | 教师签发一次性短期恢复码，服务端验证后接续；不能仅输入UUID任意接管 |
| 名称相同 | 允许显示名冲突，数据始终按UUID；需要时增加展示后缀 |

`POST /api/players/switch` 必须校验当前会话并幂等，服务端审计 old/new UUID；旧页面的写令牌失效。`POST /api/teacher/players/:uuid/recovery-code` 签发一次性短期恢复码，`POST /api/players/recover` 使用该码换取新会话并作废旧会话。恢复码不能写进任何埋点、CSV或页面 URL。

先记录页面打开再创建 UUID：客户端为本次初始化生成 bootstrap_id 和 page_instance_id，将 page.opened/创建请求等暂存 bootstrap 流。服务器登记成功返回 UUID 并绑定该流；持久化导出时全部关联该玩家，保留 original_bootstrap_id，不重建 event_id。创建失败保留待关联日志，未成功不能开始正式题。

浏览器 bootstrap_id/page_instance_id 可用 HTTPS 下的 `crypto.randomUUID()`；它生成安全随机 v4 UUID。能力不可用时改由服务器签发，不用时间戳或 `Math.random()` 拼身份。[MDN randomUUID](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)

玩家信息只有 player_uuid、随机称呼、语言经历与经验区间。场次使用独立session_id，同一玩家可能参加多个场次；学习语言/经验变更记录前后值，成绩保留开轮时的profile_version。

## 2. 记录哪些交互

[玩家交互埋点清单](玩家交互埋点清单.md)与`interaction_catalog.json`定义 **77 种交互位置模式**和 **32 种系统节点/结果事件**。动态模式不是只记录一个样例，而是为每个关卡、代码行、输入框、棋盘格生成独立element_id。

### 2.1 双层记录

**原始交互层**：记录浏览器实际分发给任务界面的 pointerdown/up、click、dblclick、contextmenu、focusin/out、keydown/up、beforeinput、input、change、compositionstart/update/end、paste/copy/cut、scroll、pointerenter/leave。包括没有导致状态变化的操作。

**语义与规则层**：记录进入关卡、选择顺序、修改代码、请求运行、校验错误、命令派发、成功移动、撞墙、拾取、停止、重来、结果、同步。没有玩家操作也可能出现系统时间节点。

两层以 interaction_id 串联。一次按键可能产生 raw_interaction、key_observed、command、movement、coin 五条日志，分析时按 interaction_id 计一次操作；步数只以服务端重放的成功移动计。

不要求持续采集没有产品语义的鼠标移动像素、操作系统未派发事件或浏览器外按键。任务中的每个实际交互事件必须逐条保留；鼠标进入/离开、滚动、聚焦等注册事件不能用“没影响成绩”为由删掉。

### 2.2 输入必须可逐次恢复

- 每个 `input` 保存字段旧值、新值、inputType、selection_before/after（若控件支持）、field_revision、program_revision、is_composing。用户从“1”变“12”再删成“1”，三次变化都在，不能只记最终“1”。
- beforeinput 用于记录修改意图，input 以实际新值为准。有些输入方式不触发可取消的 beforeinput，因此不能只监听它。[MDN beforeinput](https://developer.mozilla.org/en-US/docs/Web/API/Element/beforeinput_event)
- IME 的composition事件与input都保留，但只有确认后的规范字段修订更新最终可运行程序，不能因为多事件把一个汉字当多次代码插入。
- 粘贴/剪切/撤销也记录inputType与值变化；剪贴板只记录写入/取自本任务字段的结果，不读取或上传无关剪贴板内容。
- 仅本任务的方向、次数、预计步数、选项值可逐字符保存。场次码记录编辑次数和长度变化，恢复码/认证字段只记操作结果，绝不采集其内容。
- 每次字段修订递增版本；稳定row_id不会因行号变化重用；删行事件带旧行，新增带新UUID。最终程序快照加校验散列，用来检查修订链是否可还原。
- 错误方向、超范围次数、未完成空格都保留输入事件与校验反馈；格式错误不消耗正式次数。旧版800ms防抖保存输入的约定在V2取消。

## 3. 通用 envelope 与时间

所有字段固定存在，业务尚未发生时允许下表指定的 null；不靠删字段表示未知。

```json
{
  "schema_version": "2.0.0",
  "event_id": "事件UUID",
  "player_uuid": "玩家UUID",
  "session_id": "场次UUID或null",
  "assignment_key": "P14或null",
  "level_id": "L14或null",
  "mode": "python_blank或keyboard或null",
  "attempt_id": "开轮前null，开轮后服务端UUID",
  "stream_id": "当前流UUID",
  "seq": 127,
  "event_type": "python.field_edited",
  "element_id": "python.row.row-uuid-3.count",
  "interaction_id": "本次交互UUID，系统事件可null",
  "client_time": "2026-09-09T02:15:00.120Z",
  "page_instance_id": "此次页面UUID",
  "mono_ms": 25120.31,
  "elapsed_ms": 93450.00,
  "payload": {
    "row_id": "row-uuid-3",
    "field": "count",
    "old_value": "1",
    "new_value": "12",
    "input_type": "insertText",
    "field_revision": 3,
    "program_revision": 8,
    "is_composing": false,
    "selection_before": [1, 1],
    "selection_after": [2, 2]
  }
}
```

上例是结构说明，不是真实学生数据。`telemetry.example.jsonl` 是13条虚构轮次事件，演示K01右移两步到成功的因果链；只是一段前缀示例，不代表完整场次或全覆盖样例。

内容相关流还需 `content_version`、`rules_version`、`config_hash`，可在 stream 元数据固定保存，导出时展开到每条事件。服务器新增 server_received_at、actor绑定、payload_hash、validation_status；不接受客户端自己声称的server时间。

| 时间 | 来源与用途 |
|---|---|
| client_time | ISO UTC墙钟，方便理解现场时点；时钟可被更改，不当裁判排序依据 |
| mono_ms | 当前page的performance.now，相对单调时钟 |
| elapsed_ms | 当前流累计有效打开时间：恢复的累计偏移 + 本页单调增量；关闭期间间隔另存，不伪装连续在线 |
| server_received_at | 服务器写入时间，用于同步延迟、截止与收卷 |
| visibility/focus事件 | 计算可见、前台、失焦、离开、暂停区间 |

`performance.now()`采用相对单调时钟，用来测页面内间隔；跨页不能直接相减。睡眠/挂起的时间差另用墙钟和生命周期作辅助观察，不能宣称所有设备休眠计时一致。[MDN performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)

必须能派生：页面加载、关卡首次可操作、读题、首次交互、首次计划、首次代码编辑、首次运行、第一步、各金币拾取、首次成功、每次重来、提示停留、代码执行、暂停/失焦、离开、同步确认。计划时间以level.ready到attempt.started分解，并结合输入编辑事件；不要把读题、填代码、动画与网络等待全部叫“解题时间”。

## 4. 流、作用域与因果关系

| 流 | 生命周期 | 放什么 |
|---|---|---|
| bootstrap | 本次页面首次登记前，之后绑定玩家 | 最早页面打开、身份创建失败/重试 |
| player/session | 已登记玩家的入口与场次导航 | 复制UUID、语言修改、选模式、声音、导航、反馈 |
| assignment | 进入某一K/P关至离开 | 读题、计划、代码编辑、教学、提示、未开轮错误 |
| attempt | 一次正式/练习运行开始至终止 | 原始执行输入、命令、移动、金币、轮次结果 |
| system | 每页面运行期 | 网络、存储、同步、生命周期与技术异常 |

每流的seq独立从1递增，刷新在相同流继续编号；page_instance_id变。多个流不能用seq互相排序，依赖interaction_id、page_instance_id、mono_ms和显式关联。不同标签页各有流，不能抢同一个本地seq计数器。

原始DOM事件在其发生时确定一个主流，仅写一次；语义事件可写相应业务流并引用interaction_id。在“运行”点击后才创建attempt时，点击原始事件属于assignment流，attempt.started记录trigger_interaction_id来连接，不能把已经保存的旧事件移来移去。

attempt.finalized之后该轮流冻结。玩家随后松键、继续按键、打开结果或点击下一关，仍在assignment/session流记录（按键disposition=ignored、reason=finished），不是停止采集。这样既保留终止后的行为，也不让已收卷的轮次流无限增长。

流登记使用`POST /api/event-streams`，请求scope、client_stream_uuid、关联assignment/attempt和内容版本；服务器按当前安全会话检查归属并幂等绑定，不能让客户端将流挂到别人的玩家。bootstrap尚无身份时先在本机暂存player_uuid=null；bootstrap成功才关联并上传为该玩家流。最终正常导出的学生事件必须有player_uuid；仍无法关联的初始化故障单列技术记录，不纳入学生成绩。

系统事件和DEMO播放不虚构玩家按键。每条实际命令带command_id、command_index、interaction_id；代码持续运行时多个命令可引用同一次run交互，并另带row_id和repeat_index。原始输入数量、命令数量、成功步数、收集数各自计算。

## 5. 埋点实现约定

1. 在任务根容器安装capture阶段通用观测器，取最近的data-track-id；绑定单个handler，不因React重渲染重复订阅。
2. raw记录必须先于业务处理。UI处理函数用同一interaction_id发语义事件；不要另建ID切断因果。
3. 任务内有意义的键盘数据可记录code/key/repeat/modifiers/phase，但认证字段不记录字符。direction按钮原始pointer和click均记录，只在activate派发一次命令。
4. 原生disabled按钮可能不分发click；需要观察拒绝操作的控件使用可聚焦的aria-disabled外层拦截，记录disposition=blocked及reason，不执行业务。不能把“没收到click”当玩家没点过。
5. hover/focus开出的提示卡要有shown/closed时间；scroll按浏览器实际派发逐条记录位置，网络可批量，不能丢弃事件。装饰元素没有独立行为时归属最近组件，不虚构每个像素都是交互。
6. 注册表兜底`interactive.{element_id}`仅用于检测漏注册，不能算完成映射。检测到新控件缺少专用注册时发telemetry.registration_missing，开发构建/验收失败；所有动态实例需要匹配正确专用规则。
7. 每个事件记录disposition（observed/accepted/ignored/blocked/invalid）和reason（如repeat、focus_in_editor、not_started、finished、budget、readonly）。无效和取消都不能省略。
8. 去抖只能用于视觉渲染或批量网络发送，不能合并、采样或覆盖已经生成的交互事件。若容量不足应暂停并提示，不能悄悄删除早期记录。

## 6. 存储、重试与完整性

事件先逐条进入有序outbox，立即安排IndexedDB事务持久化。命令/世界状态/派生事件原子写入。UI只有持久化确认后才显示“本机已保存”，不能仅凭内存数组成功。硬崩溃在落盘前的极短窗口可能丢失，不声称绝对零丢；恢复时以最后已持久化seq/快照为准并报告检测到的间隙。

正常每2秒或积累40条发送一批，每批最多200条或256KiB，按大小先到者切批。批中每个event_id/seq原样保留。重试1/2/4/8/16/30秒上限30秒加抖动；断网后本机继续，恢复后按批补传。不为每个按键发HTTP请求。

服务端约束event_id全局唯一、(stream_id,seq)唯一；相同ID同内容重传幂等，相同ID不同内容409冲突。乱序可暂存，只确认连续前缀并返回missing_ranges；本机只删除已明确确认的outbox段。身份、stream所属和内容版本都校验，不能仅相信envelope中的player_uuid。

**全量日志含开轮前的编辑、进入页面和取消操作**。因此finalize除了attempt流final_seq，还包含本次轮次关联的assignment/player/bootstrap流高水位和program_snapshot_hash。服务器确认这些要求范围完整后才能将 `interaction_integrity=complete`。之后继续发生的新编辑不会追溯改变已冻结高水位，但结束整关/场次还需提交各流最新高水位。

成绩验证和日志完整性两个状态并列：命令足够可先算provisional_score；任何必需流有缺段，verified_score可暂为true但interaction_integrity必须为pending，最终收卷状态仍pending。服务器不能仅靠最后代码正确就判全量埋点完整。

同步自身日志归属system流，不能触发无限“确认日志又产生确认日志”的递归收卷。规则：冻结要上传的session结束高水位后，最后一次收卷传输ACK只在服务器request_audit记录，不在冻结流追加新客户端事件；后续健康事件归新的运维流，不影响已冻结成绩与交互完整度。平时sync事件也按固定周期批量发送，不因每个ACK立即新建网络批次。

本机存储失败/接近配额时暂停正式输入，提示联系老师，可下载匿名诊断包。暂停与恢复也记录。刷新时复用同一个未终止attempt，恢复程序执行前缀，清空尚未派发的键盘队列并发恢复事件。离线不能新开正式轮次，未同步不能显示全场收卷成功。

关闭页前flush是尽力而为，不能依赖beforeunload或sendBeacon保证所有记录到达。学生再次打开应继续补传；场次截止后补传的离线数据保留needs_review，教师现场证据确认并审计。

## 7. 交互验收必须落到实际页面

自动扫描所有button、a、input、select、textarea、tab、可点击role和有事件handler的自定义控件，检查data-track-id和专用注册。对每种动态模式至少覆盖首/中/末实例：K01/K10/K20、P01/P10/P20、首末代码行、金币/障碍/空格。

逐项执行清单中的77种操作模式，并用事件记录检查：原始事件存在、语义结果存在、同interaction因果正确、时点合理、成功/失败/取消/只读路径不缺项。检查32种系统节点的可达场景；极端故障用注入方式测试而不破坏真实学生数据。

重点脚本：复制UUID→选择语言→进P14→依次填1、12、删除2→粘贴方向→删行→取消重来→打开关闭API→运行→撞墙→停止→再次运行→刷新→断网→完成→恢复网络→收卷。必须能按事件重建各次输入与世界状态；只保留最终程序的实现应验收失败。

另需测键盘长按、快速方向切换、编辑框方向键、IME、空白/小数/超范围、点击禁用运行、滚动、静音、知识检查首答/修改、全部弹窗取消。上传时模拟重复/缺一段/乱序，最终数据库事件数等于客户端冻结清单，event_id不重复。

本包提供注册表和样例结构校验，**尚未提供实际页面上的全量埋点实现或覆盖率证据**。开发完成后必须交付浏览器交互报告和可导出的真实测试事件，不能用此77条清单本身证明功能已实现。

## 内容2.1补充：最多6枚金币的交互

计划顺序和金币提示按本关实际金币数生成1～6个槽位、A～F标签；`plan.order.{slot}`必须覆盖第4/5/6槽，`board.cell.{x}.{y}`覆盖10×10地图实际可见格。逐槽选择、替换、清空、重来和被校验拒绝仍逐次埋点，不另造只记录前三枚的事件结构。`coin.collected`的actual_order_index取1～6；开轮计划快照、实际顺序、进度分母和教师导出必须包含全部金币。埋点schema保持2.0.0，内容流关联content_version=2.1.0。
